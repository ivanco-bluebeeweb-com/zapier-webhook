## Прогон 2026-08-20 — Части A-C (персона, данные, сценарии) + Часть D

**Персона:** владелец Zapier-аккаунта (единственная функциональная роль
этого приложения — узкий двунаправленный мост, не полноценный коннектор
со списком команд/проектов). Он настраивает ОБЕ стороны моста: вставляет
Catch Hook URL, чтобы события уходили ИЗ Imperal в Zap, и генерирует общий
секрет, чтобы шаг «Webhooks by Zapier» в Zap мог присылать события ОБРАТНО
в Imperal. Вариативность сценариев — из классов данных (пусто/типично/
граница/невалидно/экзотика), не из ролей.

**5 обязательных веток покрыты** (см. `tests/test_pst_scenarios.py`):
1. **Empty** — ничего не настроено: `get_outgoing_webhook_status`,
   `get_inbound_webhook_config`, `send_webhook_event` без URL,
   `receive_zapier_webhook` без секрета — все дают честный, понятный ответ,
   не падение.
2. **Typical** — happy path обеих сторон: сохранить исходящий URL, отправить
   событие (успех), сгенерировать входящий секрет, принять валидный POST с
   верным заголовком `X-Zapier-Webhook-Secret`, прочитать список событий.
3. **Boundary** — очистка URL пустой строкой (явный no-op сценарий, не
   ошибка); повторная генерация секрета (ротация: старый сразу перестаёт
   приниматься).
4. **Invalid** — URL без `http(s)://` префикса отклоняется с понятной
   ошибкой ДО сохранения; неверный/отсутствующий заголовок секрета на
   входящем webhook отклоняется `hmac.compare_digest` (не голым `==`).
5. **Exotic / Soap Opera** — сетевой сбой при отправке (DNS/timeout) и
   не-2xx ответ от Zapier конвертируются в контролируемую ошибку, не в
   необработанное исключение; повторная доставка одного и того же payload
   (Zap retry после timeout) намеренно создаёт ВТОРУЮ запись в списке
   событий, а не дедуплицируется — задокументировано как осознанное
   поведение (не наш баг, ответственность самого Zap за идемпотентность).

**D1 (Deploy Verification):** применялось после фиксов ниже — код
приложения менялся. `imperal validate .` → 0 error / 0 warning / 1 info
(отсутствие `@ext.on_install`, ожидаемо для этого узкого моста).

**D2 (Idempotency):** явный тест на повторную доставку одного и того же
inbound-события (см. Branch 5 выше) — подтверждено намеренное поведение
«не дедуплицируется», не скрытый баг.

**D3 (Security/SSRF):** исходящая сторона (`set_outgoing_webhook` /
`send_webhook_event`) — та же осмысленная, уже принятая SSRF-поверхность,
что и в Make.com Connector: URL — это и есть credential, настраивает его
сам владелец аккаунта для собственного Zap, не приём произвольного адреса
от третьей стороны. Входящая сторона (`receive_zapier_webhook`) защищена
`hmac.compare_digest` constant-time сравнением общего секрета — по тому же
паттерну, что Slack Connector использует для проверки подписи.

**D4 (Regression grep):** этот прогон PST поймал живой код через реальный
`MockContext`, что вскрыло ДВА реальных, ранее незамеченных статической
сверкой бага:

1. **`ActionResult.success(data)` без обязательного `summary`** — три
   места (`get_outgoing_webhook_status`, `get_inbound_webhook_config`,
   `list_inbound_events`) вызывали фабрику без второго обязательного
   позиционного аргумента `summary: str`, что привело бы к `TypeError` при
   первом же реальном вызове любой из этих трёх read-функций. Исправлено —
   добавлен содержательный `summary` в каждый вызов.
2. **`getattr(page, "items", None)` вместо `page.data`** — `Page`
   (`imperal_sdk.types.pagination.Page`) хранит список в поле `data`, не
   `items`; оба места (`list_inbound_events` и prune-логика в
   `receive_zapier_webhook`) читали несуществующий атрибут, тихо получая
   `None → []` — события реально сохранялись в store, но НИКОГДА не
   попадали в список и никогда не обрезались по `_INBOUND_EVENTS_MAX`.
   Исправлено — оба места теперь читают `page.data`.

Оба бага задокументированы в `Docs/known-bug-patterns.md` (запись
2026-08-20) вместе с остальными находками этого прогона (несуществующие/
мёртвые kwargs на `ui.*`, найденные тем же днём в этом же и в Make.com
Connector). Portfolio-grep на паттерн `getattr(page, "items"` — см. запись
в known-bug-patterns.md — специфичен для этого файла, других совпадений в
портфеле не найдено (остальные приложения уже используют `.data` напрямую
или свою собственную query-обёртку).

**Итог:** 22/22 теста проходят (`tests/test_pst_scenarios.py` +
`tests/conftest.py`), `imperal validate .` чист, оба найденных бага
исправлены и покрыты регрессионными тестами (не откачены обратно — тест
на `page.data`/`summary` теперь ловит регресс, если кто-то в будущем
скопирует старый паттерн).
