## 1. Официальные developer-поверхности Zapier (подтверждено свежим чтением docs.zapier.com / community.zapier.com, 2026-08-20)

| Поверхность | Направление | Что реально даёт | Auth |
|---|---|---|---|
| **Platform CLI/SDK** (docs.zapier.com/integrations/build-cli) | Ingress (Zapier → Imperal становится app ВНУТРИ Zapier) | Imperal публикуется как интеграция в каталоге Zapier — пользователи Zapier добавляют "Imperal" как trigger/action в СВОИ Zap'ы. Обратное направление тому, что делают n8n/Make/Power Automate коннекторы. | OAuth1/OAuth2 middleware, задаётся самим разработчиком интеграции |
| **Webhooks by Zapier** (help.zapier.com) | Egress (одностороннее) | Встроенный в любой Zap trigger/action "Webhooks by Zapier" — можно слушать входящий POST или дёргать чужой URL по GET/POST/PUT из Zap'а. Не даёт списка/управления Zap'ами пользователя. | Нет отдельного auth — это просто HTTP endpoint внутри чужого Zap |
| **Partner API / "Powered by Zapier"** (docs.zapier.com/powered-by-zapier) | Both — READ (`GET /v2/zaps` список) и WRITE (`POST /v2/zaps` создание, `PATCH` включение/выключение) | **Это единственная поверхность, реально похожая на Make/n8n API** — настоящий REST для управления Zap'ами пользователя от имени встроенного в чужой продукт "Powered by Zapier" виджета. | OAuth с `client_id`, который выдаётся **только после создания публичной интеграции и прохождения ревью** (см. §2) |
| **AI Actions / Zapier MCP** | Both, но per-action, не CRUD над Zap'ами | Точечные экшены для AI-агентов (например, "send email", "create task") — НЕ управление самими Zap'ами/workflow, а вызов конкретных действий целевых приложений через готовые Zapier-интеграции с ними. Похоже на использование Zapier как proxy к третьим приложениям, а не на управление автоматизациями. | Zapier MCP-специфичный auth (per-account, отдельно от Platform CLI/Partner API) |

## 2. КРИТИЧНЫЙ факт, подтверждённый в этом заходе (2026-08-20) — расходится с тем, что было записано в задаче #2140 при её создании

Задача #2140 фиксировала «у Zapier нет полноценного REST API». Это неточно: **Partner API существует и даёт то же самое, что Make/n8n API** (list/create/toggle Zap). НО реальный барьер другой и более серьёзный, чем «нет API» — это **gate на доступ**:

> Прямая цитата с community.zapier.com (тред 2023, актуальность подтверждена структурой текущей доки): «The partner api to get app zaps needs a client Id which is only available if I create a public integration. It also asks a bunch of questions and the review process takes a week.»

То есть: чтобы получить `client_id` для Partner API — нужно ЗАРАНЕЕ построить и отправить на ревью публичную Zapier-интеграцию (через тот же Platform CLI/SDK из §1), и только письмо о её принятии открывает доступ к Partner API. Это классическая курица-и-яйцо: путь (в) ниже — обязательный ПРЕДШЕСТВЕННИК пути (а), а не альтернатива ему.

## 3. Классификация по типу функционала (Шаг 1 стандарта)

- **Ingress** (Zapier → пользователь Imperal): нет прямого способа получить его без прохождения через (б)/(в) ниже — Zapier не отдаёт список/детали чужих Zap'ов без Partner API access.
- **Egress** (Imperal → Zapier): доступен сразу через Webhooks by Zapier — но это НЕ управление Zap'ами, это просто вызов заранее настроенного пользователем webhook URL внутри его Zap'а (Imperal ничего не "видит" и не листает на стороне Zapier).
- **Both**: только Partner API, и только после ревью.

## 4. Ярус 1 (минимально жизнеспособный коннектор) — оценка

Ярус 1 в духе Make/n8n (BYOK API-ключ, list/run/toggle) **физически недостижим без прохождения review-процесса** — то есть Zapier не позволяет мгновенный "вставь свой ключ и работай" паттерн, которым уже пользуются все три существующих коннектора.

## 5. Три архитектурных пути (взаимоисключающие ИЛИ дополняющие, требуют явного выбора)

**(а) Egress-only через Webhooks by Zapier** — Imperal получает набор функций типа "отправить событие в заданный Zapier webhook URL" (пользователь сам создаёт Zap с триггером Webhooks by Zapier и вставляет URL в настройки коннектора). Быстро, без ревью, но НЕ похоже на Make/n8n UX — Imperal не видит и не управляет Zap'ами пользователя, только шлёт данные в один заранее заданный URL. Ограниченная ценность.

**(б) Imperal как Zapier-приложение (Platform CLI/SDK, ingress)** — зеркальное направление: строим интеграцию, которая появляется в каталоге Zapier, и уже ПОЛЬЗОВАТЕЛИ ZAPIER добавляют "Imperal" как trigger/action в свои Zap'ы (например, "когда в Imperal что-то происходит → запустить Zap" или "Zap может дёрнуть функцию Imperal"). Другая аудитория (юзеры Zapier, не юзеры Imperal-чата), другой процесс релиза (публикация и ревью в Zapier App Directory), совершенно другой код (Node.js, Zapier Platform SDK, не наш `imperal_sdk`).

**(в) Partner API путь** — сначала пройти (б) (обязательная публичная интеграция + ревью ~1 неделя), ПОТОМ получить client_id, ПОТОМ построить настоящий Make/n8n-подобный коннектор с list/create/toggle Zap. Самый близкий к тому, что уже есть у трёх существующих коннекторов по UX, но самый долгий и с внешней зависимостью (ревью командой Zapier, не под нашим контролем по срокам).

## 6. Решение по объёму этого захода — ТРЕБУЕТ выбора Влада

Ещё не принято. Варианты для явного решения:
1. Начать с (а) — Egress через Webhooks by Zapier — самый быстрый релиз, честно ограниченный по функциональности (одно поле "webhook URL" + функция отправки события), НЕ похож на Make/n8n по глубине.
2. Начать с (б) — построить Imperal как приложение внутри каталога Zapier (другой тип проекта, другой SDK, другая аудитория — не то же самое "коннектор в Imperal", а зеркальный проект).
3. Пойти по (в) — начать процесс регистрации публичной интеграции ради доступа к Partner API, зная что реальный полноценный Zapier-коннектор появится не раньше, чем через ~1+ неделю (внешняя зависимость от ревью Zapier).
4. Комбинация — например (а) сейчас как быстрый релиз, параллельно запустить процесс (б)→(в) для полноценной версии позже.

**Без этого решения Фаза 3 (дизайн/код) не начинается** — так требует сам стандарт, и в данном случае это не формальность: три пути дают принципиально разный код, разную аудиторию и разные сроки.
